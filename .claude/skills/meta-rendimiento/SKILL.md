# Meta rendimiento: varias cuentas por proyecto, copia de métricas y la pestaña Meta

> Parte de la guía del repositorio. **Si cambias esta área, actualiza este archivo** en el mismo cambio (no CLAUDE.md). Si el código y este texto no coinciden, manda el código: corrige el texto.

**Meta rendimiento** (package `meta_rendimiento/`, `tareas/meta_rendimiento.py`, migration 0034 — it was 0033 in the branch and was renumbered when main brought `0033_cobros`, 2026-10-08; spec `docs/superpowers/specs/2026-10-08-meta-rendimiento-design.md`, plan `docs/superpowers/plans/2026-10-08-meta-rendimiento-e1.md`, ledger of rulings R1–R18 in `.superpowers/sdd/2026-10-08-meta-rendimiento-e1/progress.md`): a project READS the metrics of several Meta ad accounts through its one Meta token and shows them in the «Meta» tab (`_tab_meta.html`, anchor `#meta`). It never changes anything in Meta and nothing here charges anyone; launching experiments stays with the single account of `meta.json` (`experimentos` and `meta-y-publicacion` skills). Why it exists: happyflops has 7 ad accounts (all SEK, ~9 600 ads with data in 90 days, ~660 active ad sets, ~60 % in limited learning) and Daniel could not see them together. This is E1 (read + show). E2 «Diagnosticar y recomendar» and E3 «Aplicar cambios» (spec §9–§10) are not built: PND-179 and PND-180.

**Modules and single writers.** `cuentas.py` is the ONLY writer of `meta_cuenta` (the accounts a project reads: `elegir` leaves exactly the checked accounts, `cambiar_pais`, `actualizar`, `actualizar_extra` takes the row lock BEFORE reading with a no-op UPDATE — the `experimentos._bloquear` pattern — because web and worker both write `extra`; `adivinar_pais` guesses the country from the account name, an ISO code only as the LAST word so «HappyFlops AD Account» gives None). A removed account deletes its copies FIRST and its row after, so a failed removal is retried by the next `elegir` instead of leaving orphan copies. `datos.py` is the ONLY writer of `meta_cuenta_dia`, `meta_anuncio_dia`, `meta_objeto` and `meta_alcance` (every write is one transaction; `reemplazar_*` deletes the account's range and rewrites it) and holds the reads, each ONE aggregated query filtered by cliente + accounts + dates (an empty account list returns empty without touching the database). `tasas.py` is the ONLY writer of `tasa_cambio`. `graph.py` reads the Graph API with the token and the account as ARGUMENTS and never touches `meta_ads.auth`, the global state behind the launcher's lock: copying 7 accounts in a worker thread must not block a launch. `sync.py` copies ONE account, `panel.py` builds the tab, `rutas.py` is the blueprint `/cliente/<c>/meta-rendimiento`, `grafico.py` draws the day-by-day chart (it lived in `dashboard._grafico_tablero` until main deleted it on 2026-10-08; it moved here unchanged with its CSS in `static/estilos/pantallas/meta.css`).

**Tables and retention (migration 0034).** `meta_cuenta` (unique `ad_account_id` across ALL projects, `uq_meta_cuenta_act`: one account belongs to one project, so a client's data never shows in another; `estado` nueva|copiando|ok|error; `extra` holds the markers `backfill_cuenta`, `backfill_anuncios`, `backfill_hecho`, `cuenta_desde`, `anuncios_desde`, `listado_completo_en` and Meta's `cuenta{account_status, disable_reason, amount_spent, spend_cap}`); `meta_cuenta_dia` keeps 13 months (395 days) of the account per day; `meta_anuncio_dia` keeps 90 days per ad per day and `meta_rend_limpiar` (daily) deletes rows older than 95; `meta_objeto` is campaign/ad set/ad (name, `estado` = Meta's `effective_status`, budgets, `aprendizaje` = `learning_stage_info.status`, thumbnail, `video_id`), unique by (cliente, objeto_id); `meta_alcance` is reach and frequency per window 7/14/30/90 days at level cuenta|campana; `tasa_cambio` (fecha, moneda, `usd_por_unidad`) is global, not per project. `guardar_objetos` updates only the columns PRESENT in each dict: the insights give names without `estado`, and a full overwrite would blank every status and thumbnail every 3 h.

**The copy.** Task `meta_rend_sincronizar`, ONE per account, `job_id` `<cliente>__meta_rend__<act>` (`tareas.meta_rendimiento.job_id_sync`), `max_intentos=2` (reading never charges), priority 2 so Crear and experiments go first; it is listed in `TIPOS_EXENTOS_DE_COBRO` with the other `meta_rend_*` tasks (a project with «Cobrar» on still syncs; a new Meta-reading task needs its own entry or `tests/test_cobros_worker.py` fails). The periodic `meta_rend_sincronizar_todas` (every 3 h, `worker.PERIODICAS`) enqueues every account of every project. It runs in the worker lane `lectura` with ONE thread (`CARRIL_LECTURA`, see `plataforma`): measured on the real API, a first copy takes 8 min (Norway) to 14 min (Netherlands), ~2 min incremental, peak ~118 MB; on the single general thread 7 first copies (~1 h) would have blocked experiment launches and Triple Whale. Accounts copy one after another on purpose: Meta's rate limit is per user + app and shared by every project using that user and app (colorado_forja's experiments hit it too), and it answers code 17 «user request limit» when exhausted. So the first copy is RESUMABLE: it goes from the newest chunk to the oldest (`_plan`, `_tramos_atras`: account 90-day chunks, ads 10-day chunks) and writes `cuenta_desde`/`anuncios_desde` after each chunk; a failure (code 17, a restart) leaves the account in `copiando`/`error` and the next run repeats the recent days and continues backwards from the marker instead of starting over. `backfill_cuenta` and `backfill_anuncios` are separate flags so a late failure does not redo a finished part. After the first copy only the last 7 days are re-read (Meta re-attributes purchases of past days), starting at the last stored day if the gap is longer, and that range is deleted and rewritten. `hoy` is the account's local date (`timezone_name`), because Meta cuts days in that zone. The full ads listing (paused ads with light fields, then `marcar_sin_estado` for what neither list returned: archived or deleted) runs at most every 20 h (`extra.listado_completo_en`); each run lists campaigns, ad sets and the ads that deliver or wait (with `creative{…}` for the thumbnail). Graph pagination follows `cursors.after`, never `paging.next` (that URL carries the token); on Meta code 1 or 2 («reduce the amount of data») `graph.paginar` halves `limit` (down to 25, 3 times) and retries the SAME page, which is why ads start at 100 per page; it RAISES at the page cap instead of returning what it read (a partial chunk would be written as if complete); `graph.informe` (async insights for `level=ad`) polls with a growing wait 5→30 s because every poll counts against the limit. Each insights page is turned into small rows on arrival (`por_pagina`; a raw row weighs ~8 KB and the VPS has 2 GB). Rates: `tasas.asegurar` runs from the OLDEST stored account day, not from this run's window (a first copy spread over several runs would leave old days without USD). `tareas.meta_rendimiento` catches ANY exception, saves a token-free message in the account (`estado=error`) and re-raises a `RuntimeError` from None so the queue retries; the `al_interrumpir` hook turns a `copiando` account killed by a restart into `error`. A first copy can outlast `TimeoutStopSec=600` of the worker; it resumes after the restart (PND-187).

**The tab.** `_tab_meta.html` paints only a frame on page load (`meta_rend` = connected, `n_cuentas`, `modo`); the panel arrives by fetch when the tab opens (`ver_panel` → `_meta_panel.html`, `panel.contexto(cliente, dias, cuenta)`; `dias` ∈ 7/14/30/90, default 30; `cuenta` empty or foreign = «Todas»). Rendering NEVER calls Meta, Claude or the BCE: it reads the copy and the saved rates (`tasas.mapa`), in about 15 queries (`kpis`, `serie`, «Por cuenta», campaigns, ad sets with «Ver más», ads with «Ver más» via `ver_conjuntos`/`ver_anuncios`, which return only `<tr>` rows). «Todas» with two or more accounts shows USD: each day of each account is converted with ITS rate of that day (`_conversion`); if a day with spend has no rate, the USD amounts are None and the screen says «USD no disponible» — never an invented rate — and the chart falls back to the common currency when there is one. One account shows its own currency. Campaigns, ad sets and ads always show the currency of their account (each row carries `moneda`). Each ad is evaluated against ITS account: `triple_whale.evaluacion.evaluar` runs once per account over one read per window (period, last 7 days, the 7 before for fatigue), the `sin_rastreo` problem is dropped (it speaks of Triple Whale parameters), and the verdict labels are Triple Whale's. The sync bar is `data-poll-job` over `syncs_en_curso`. The only route that calls Meta when opened is `cuentas` (GET, the «Elegir cuentas» selector → `meta_conexion.listar_activos`); `cuentas` (POST) adds only accounts the token SEES (an id typed by hand is ignored), keeps ones already in the project even if the token no longer sees them, and enqueues the first copy of each new one; `cuentas/<act>/pais` changes a country (404 foreign, 400 bad code); `sincronizar` is «Actualizar ahora». Every POST rejects `Sec-Fetch-Site` other than same-origin/none. In agency mode the selector says «Todavía no disponible» (spec §2.10; PND-184).

**Page optional (2026-10-08).** A project connected without a Facebook Page is «solo métricas»: this tab works fully, and launching and publishing stop in words before any call to Meta. The guards and `meta_conexion.sin_pagina` are in `meta-y-publicacion` («Conexión solo métricas»); reading the copy never needs a Page.

**Traps.** (1) The token never reaches an error, flash, event, log or template: `graph` summarizes a network error with `type(e).__name__` (the `str` of a `requests` exception carries the URL with `access_token`), Meta's text goes through `cola.sin_token` and the exact token value is struck out; `paging.next` carries the token, so it is never logged or followed. (2) Reach is unique people: it is NOT additive across days or accounts (`totales_por_cuenta` leaves it out on purpose; the period's reach comes from `datos.alcance` at the nearest window, and «Todas» shows the sum of per-account reach, so people on two accounts count twice). Reach of a campaign that stopped delivering stays at its last value (PND-186). (3) Budgets arrive in the currency's minor unit as text (`sync._presupuesto` divides by 100 except `tareas.meta.MONEDAS_SIN_DECIMALES`), and «0» means no budget at that level (budgets are mostly on the ad set), never 0. (4) `estado` has two odd values: `ARCHIVED` and None (Meta no longer lists it); both have labels in `panel.ESTADOS`. An ad paused or archived after the last full listing keeps showing `ACTIVE` for up to ~20 h, because the 3-hourly runs list only the ads that deliver or wait and `datos.activos` counts that stale state. (5) Purchases are the first present type of `graph.TIPOS_COMPRA` (`purchase`, `omni_purchase`, `offsite_conversion.fb_pixel_purchase`), never their sum. (6) Thumbnails are Meta's signed URLs hot-linked with `loading="lazy"`: they expire and the picture breaks until the next copy refreshes the URL (PND-181). (7) The ad set's frequency is not copied, only account and campaign reach (PND-182). (8) «Todas» orders by the nominal amount, so with mixed currencies the order is not by value (PND-183). (9) Every user-visible string of the package goes through the catalog (`PAQUETES` in `catalogo_i18n.py` includes `meta_rendimiento`; the statuses live in `panel.ESTADOS`/`APRENDIZAJE`/`OBJETIVOS` with `N_`). (10) The first real copy of a new account is the only real test of a change to `sync.py`: run it against a copy of the database (the lessons of the Norway and Netherlands runs are the rulings R8–R14).
