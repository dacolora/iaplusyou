# Meta rendimiento: varias cuentas por proyecto, copia de métricas y la pestaña Meta

> Parte de la guía del repositorio. **Si cambias esta área, actualiza este archivo** en el mismo cambio (no CLAUDE.md). Si el código y este texto no coinciden, manda el código: corrige el texto.

**Meta rendimiento** (package `meta_rendimiento/`, `tareas/meta_rendimiento.py`, migration 0035 — it was 0033 in the branch, renumbered to 0034 when main brought `0033_cobros` (2026-10-08) and to 0035 when main brought `0034_tw_tarjetas` (2026-10-09); spec `docs/superpowers/specs/2026-10-08-meta-rendimiento-design.md`, plan `docs/superpowers/plans/2026-10-08-meta-rendimiento-e1.md`, decisions and rulings R1–R30 with their reasons and the numbers measured against the real API in `docs/superpowers/decisiones/2026-10-08-meta-rendimiento-e1.md`): a project READS the metrics of several Meta ad accounts through its one Meta token and shows them in the «Meta» tab (`_tab_meta.html`, anchor `#meta`). It never changes anything in Meta and nothing here charges anyone except E2's «Evaluar con IA» (below); launching experiments stays with the single account of `meta.json` (`experimentos` and `meta-y-publicacion` skills). Why it exists: happyflops has 7 ad accounts (all SEK, ~9 600 ads with data in 90 days, ~660 active ad sets, ~60 % in limited learning) and Daniel could not see them together. **Who picks the accounts: only an admin** (R20, below). This started as E1 (read + show) and E2 «Diagnosticar y recomendar» (rules, breakdowns, «Evaluar con IA», Alertas; built 2026-10-10 on branch `meta-e2`, spec `docs/superpowers/specs/2026-10-10-meta-rendimiento-e2-design.md` with its §14 «Cambios tras la construcción», decisions E2-R1–E2-R8 in `docs/superpowers/decisiones/2026-10-10-meta-rendimiento-e2.md`, price measured in `docs/superpowers/evals/2026-10-10-meta-evaluacion.md`) is described below; PND-192 «hecho sin probar en real», leftovers PND-257–PND-270. E3 «Aplicar cambios» (spec §10) is not built and waits for Daniel: PND-193.

**Modules and single writers.** `cuentas.py` is the ONLY writer of `meta_cuenta` (the accounts a project reads: `elegir` leaves exactly the checked accounts, `cambiar_pais`, `actualizar`, `actualizar_extra` takes the row lock BEFORE reading with a no-op UPDATE — the `experimentos._bloquear` pattern — because web and worker both write `extra`; `adivinar_pais` guesses the country from the account name, an ISO code only as the LAST word so «HappyFlops AD Account» gives None). A removed account deletes its copies FIRST and its row after, so a failed removal is retried by the next `elegir` instead of leaving orphan copies. `datos.py` is the ONLY writer of `meta_cuenta_dia`, `meta_anuncio_dia`, `meta_objeto` and `meta_alcance` (every write is one transaction; `reemplazar_*` deletes the account's range and rewrites it) and holds the reads, each ONE aggregated query filtered by cliente + accounts + dates (an empty account list returns empty without touching the database). `tasas.py` is the ONLY writer of `tasa_cambio`. `pausa.py` is the ONLY writer of the `kv` row `meta_rend:pausa_hasta` (the shared pause, see «Meta's usage limit»). `graph.py` reads the Graph API with the token and the account as ARGUMENTS and never touches `meta_ads.auth`, the global state behind the launcher's lock: copying 7 accounts in a worker thread must not block a launch. `sync.py` copies ONE account, `panel.py` builds the tab, `rutas.py` is the blueprint `/cliente/<c>/meta-rendimiento`, `grafico.py` draws the day-by-day chart (it lived in `dashboard._grafico_tablero` until main deleted it on 2026-10-08; it moved here unchanged with its CSS in `static/estilos/pantallas/meta.css`).

**Tables and retention (migration 0035).** `meta_cuenta` (unique `ad_account_id` across ALL projects, `uq_meta_cuenta_act`: one account belongs to one project, so a client's data never shows in another; `estado` nueva|copiando|ok|error; `extra` holds the markers `backfill_cuenta`, `backfill_anuncios`, `backfill_hecho`, `cuenta_desde`, `anuncios_desde`, `listado_completo_en` and Meta's `cuenta{account_status, disable_reason, amount_spent, spend_cap}`); `meta_cuenta_dia` keeps the account per day for 400 days (the first copy brings 395) and `meta_anuncio_dia` keeps 90 days per ad per day: `meta_rend_limpiar` (daily) deletes ad days older than 95 and account days older than 400 (`datos.purgar_cuenta_dias`, for ALL projects); `meta_objeto` is campaign/ad set/ad (name, `estado` = Meta's `effective_status`, budgets, `aprendizaje` = `learning_stage_info.status`, thumbnail, `video_id`), unique by (cliente, objeto_id); `meta_alcance` is reach and frequency per window 7/14/30/90 days at level cuenta|campana; `tasa_cambio` (fecha, moneda, `usd_por_unidad`) is global, not per project. `guardar_objetos` updates only the columns PRESENT in each dict: the insights give names without `estado`, and a full overwrite would blank every status and thumbnail every 3 h.

**E2 tables, the single writer and the breakdowns step (migration 0039, 2026-10-10).** E2 adds two tables in `0039_meta_rendimiento_e2` (built as 0036 on the branch; main brought 0036 `tw_visitantes`, 0037 `tw_gancho` and 0038 `planes_wompi`, so at the merge it became `0039` with `down_revision = '0038'`). `meta_desglose` (cliente, `ad_account_id`, `ventana` 7|30, `dimension` edad_genero|ubicacion|pais|dispositivo, `clave`, gasto/impresiones/clics/clics_salida/compras/valor, `calculado_en`; unique `uq_meta_desglose` over cliente + account + ventana + dimension + clave) is a copy of an account's breakdowns, replaced whole per (account, window, dimension). `meta_evaluacion` (cliente, `creado_en`, `estado` en_cola|analizando|lista|error, `cuentas`, `desde`/`hasta`, `moneda`, `muestra`, `recomendaciones`, `resultado`, `usd`, `error`, `tarea_id`, `pedido_por`, `extra`; AUTOINCREMENT so a deleted id is never reused; index `ix_meta_evaluacion_cliente_creado`) is the «Evaluación con IA»: it is PAID, so removing or changing accounts never deletes it (`datos.borrar_cuenta` leaves it; `borrar_evaluaciones` is called ONLY by `dashboard._soltar_cuentas_meta`, see «Disconnecting»). **`datos.py` is the ONLY writer of both** (`reemplazar_desgloses`; `crear_evaluacion`, `actualizar_evaluacion` — changes only the columns given, refuses `id/cliente/creado_en/actualizado_en` and an unknown `estado`, returns False when the row no longer exists —, `borrar_evaluacion`, `borrar_evaluaciones`) and holds their reads (`desgloses`, `evaluacion(cliente, id)` — the web and worker load it with the project —, `evaluaciones`, `evaluaciones_panel`). Step 7 of the copy is `desgloses.copiar(cliente, act, token)`, at most every 20 h per account (`extra.desglose_en`, the same `_listado_vencido` rule as the full listing: Meta's usage limit is shared by every project, 8 requests per account per day is the budget): 8 requests (windows 7 and 30 × 4 dimensions: `age,gender`, `publisher_platform,platform_position`, `country`, `impression_device`; `level=account`, `date_preset=last_<n>d`, 500 per page), each replacing its own rows in one transaction (`clave` = the breakdown values joined by `|`, `unknown` for a missing one, a row with no value at all is not a segment). A usage-limit `ErrorGraph` goes up (the task sets the shared pause and the marker is NOT set); any other failure of ONE combination is logged by exception type and skipped, and the marker is set anyway (retrying on every 3-hourly run would be 64 requests a day, not 8). Consequences: a combination that keeps failing keeps its old rows (readers ignore rows older than 48 h, below), and a limit mid-step repeats the finished combinations next run (PND-265).

**The copy.** Task `meta_rend_sincronizar`, ONE per account, `job_id` `<cliente>__meta_rend__<act>` (`tareas.meta_rendimiento.job_id_sync`), `max_intentos=2` (reading never charges), priority 2 — which only orders the copies among themselves, because the copy runs in its own lane and what makes it yield to Crear and launches is the shared pause and `TIPOS_ESCRITURA_META` (next paragraph); it is listed in `TIPOS_EXENTOS_DE_COBRO` with the other `meta_rend_*` tasks (a project with «Cobrar» on still syncs; a new Meta-reading task needs its own entry or `tests/test_cobros_worker.py` fails). The periodic `meta_rend_sincronizar_todas` (every 3 h, `worker.PERIODICAS`) enqueues every account of every project. It runs in the worker lane `lectura` with ONE thread (`CARRIL_LECTURA`, see `plataforma`): measured on the real API, a first copy takes 8 min (Norway) to 14 min (Netherlands), ~2 min incremental, peak ~118 MB; on the single general thread 7 first copies (~1 h) would have blocked experiment launches and Triple Whale. Accounts copy one after another on purpose: Meta's rate limit is per user + app and shared by every project using that user and app (colorado_forja's experiments hit it too), and it answers code 17 «user request limit» when exhausted. So the first copy is RESUMABLE: it goes from the newest chunk to the oldest (`_plan`, `_tramos_atras`: account 90-day chunks, ads 10-day chunks) and writes `cuenta_desde`/`anuncios_desde` after each chunk; a failure (code 17, a restart) leaves the account in `copiando`/`error` and the next run repeats the recent days and continues backwards from the marker instead of starting over. `backfill_cuenta` and `backfill_anuncios` are separate flags so a late failure does not redo a finished part. After the first copy only the last 7 days are re-read (Meta re-attributes purchases of past days), starting at the last stored day if the gap is longer, and that range is deleted and rewritten. `hoy` is the account's local date (`timezone_name`), because Meta cuts days in that zone. The full ads listing (paused ads with light fields, then `marcar_sin_estado` for what neither list returned: archived or deleted) runs at most every 20 h (`extra.listado_completo_en`); each run lists campaigns, ad sets and the ads that deliver or wait (with `creative{…}` for the thumbnail). Graph pagination follows `cursors.after`, never `paging.next` (that URL carries the token); on Meta code 1 or 2 («reduce the amount of data») `graph.paginar` halves `limit` (down to 25, 3 times) and retries the SAME page, which is why ads start at 100 per page; it RAISES at the page cap instead of returning what it read (a partial chunk would be written as if complete); `graph.informe` (async insights for `level=ad`) polls with a growing wait 5→30 s because every poll counts against the limit. Each insights page is turned into small rows on arrival (`por_pagina`; a raw row weighs ~8 KB and the VPS has 2 GB). Graph edges are ALWAYS relative (`graph._url` never takes a full URL: the token travels in the parameters and must only reach graph.facebook.com; an empty edge is the Graph root for `?ids=`) and the async report id (`report_run_id`) must be digits or it is not used as an edge. Rates: `tasas.asegurar` runs from the OLDEST stored account day, not from this run's window (a first copy spread over several runs would leave old days without USD); what frankfurter returns is treated as foreign data: at most 1 MB is read (`MAX_BYTES_RESPUESTA`), dates and rates are validated, and a rate that jumps more than ×3 (or below a third) of the previous one is not stored (`SALTO_MAXIMO`); `tasas.mapa` fills a day without a published rate with the previous one only if it is 4 days old or less (`DIAS_RELLENO_MAX`: weekend plus a holiday), beyond that it is None and the screen says «USD no disponible». `tareas.meta_rendimiento` catches ANY exception, saves a token-free message in the account (`estado=error`) and re-raises a `RuntimeError` from None so the queue retries; the `al_interrumpir` hook turns a `copiando` account killed by a restart into `error`. A first copy can outlast `TimeoutStopSec=600` of the worker; it resumes after the restart (PND-200).

**Meta's usage limit (R22).** The usage limit is per USER + APP, and colorado_forja's experiments launch with the same user and app, so a read must never spend what a launch needs. `graph` reads the usage headers of every response (`x-app-usage`, `x-business-use-case-usage`, `x-ad-account-usage`): from 75 % in any counter (`UMBRAL_USO`), or on the codes 4/17/32/613/8000x, it raises an `ErrorGraph` with `limite=True` and `espera_min`. The task does NOT re-raise that one (an immediate retry would hit the limit again): it leaves the account in `error` with the reason, sets the shared pause (`pausa.pausar`, at least 30 min, never shortened) and ends. While the pause lasts no copy starts and `meta_rend_sincronizar_todas` enqueues nothing (neither sets an error state). A copy also yields to a task that WRITES to Meta (`tareas.meta_rendimiento.escribiendo_en_meta`; ruling R30): the ones a person triggers (`TIPOS_ESCRITURA_USUARIO`: `exp_lanzar`, `meta_publicar`, `organico_publicar`) block it while pending OR running, the periodic ones (`TIPOS_ESCRITURA_PERIODICAS`: `exp_decidir`, `exp_avanzar_todos`) only while RUNNING — `exp_avanzar_todos` fires every 10 min on the one general lane and is almost always queued behind long tasks, so blocking on a pending one left accounts uncopied for hours (PND-208). A new task that writes to Meta must be added to one of the two lists (`TIPOS_ESCRITURA_META` is their sum), and `tests/test_tareas_meta_rendimiento.py` checks every name exists in the worker registry. A yielding copy does not wait for the next periodic run: it returns `tareas.Continuar` with the same `job_id` (the bar stays alive), `ejecutar_desde` 10 min later (`ESPERA_POSPUESTA`), `max_intentos=2` (`Continuar` takes an optional `max_intentos`, passed on by `worker._terminar_y_encolar`) and the counter `pospuestas` in the payload, at most `MAX_POSPOSICIONES` = 6 times (1 hour); only after that does it end with «Copia pospuesta … La próxima copia programada la retoma.» and wait for the 3-hourly run, as it also does during the shared pause (which does not re-enqueue). The pause is capped at 24 h (`pausa.MINUTOS_MAXIMOS`) whatever Meta asks. During a pause «Actualizar ahora» enqueues nothing and flashes «Meta pidió esperar: la copia sigue a las HH:MM». The first copy is resumable, so nothing is lost; the cost is data up to 3 h older. For people who are not admin, «Actualizar ahora» waits 30 minutes since the account's last copy.

**Thumbnails.** The 3-hourly runs only store the thumbnail of the ads they list with `creative{…}` (those that deliver or wait). Once a day, in the run with the FULL listing, a last step (`sync._miniaturas`) asks Meta for the thumbnail of every ad WITH SPEND in the last 30 days that has none or an older-than-20 h one — paused ones included — through `?ids=` in batches of 50 (`creative{id,thumbnail_url,video_id}`), about 20 extra calls per account per day. Nothing in that step fails the copy (a rejected batch is skipped, a usage limit stops further batches and the next full listing retries). Only a URL that passes `datos.miniatura_valida` is stored: https, host `fbcdn.net`, `facebook.com` or `fbsbx.com` (or a subdomain) and no `access_token` anywhere.

**The tab.** `_tab_meta.html` paints only a frame on page load (`meta_rend` = connected, `n_cuentas`, `modo`); the panel arrives by fetch when the tab opens (`ver_panel` → `_meta_panel.html`, `panel.contexto(cliente, dias, cuenta)`; `dias` ∈ 7/14/30/90, default 30; `cuenta` empty or foreign = «Todas»). Rendering NEVER calls Meta, Claude or the BCE: it reads the copy and the saved rates (`tasas.mapa`), in at most 19 queries with E2 (one tells whether the project has Triple Whale; with it the NVP adds 4 more; `test_pocas_consultas_con_tres_cuentas`) (`kpis`, `serie`, «Por cuenta», campaigns, ad sets with «Ver más», ads with «Ver más» via `ver_conjuntos`/`ver_anuncios`, which return only `<tr>` rows). «Todas» with two or more accounts shows USD: each day of each account is converted with ITS rate of that day (`_conversion`); if a day with spend has no rate, the USD amounts are None and the screen says «USD no disponible» — never an invented rate — and the chart falls back to the common currency when there is one. One account shows its own currency. Campaigns, ad sets and ads always show the currency of their account (each row carries `moneda`). Each ad is evaluated against ITS account: `triple_whale.evaluacion.evaluar` runs once per account over one read per window (period, last 7 days, the 7 before for fatigue), the `sin_rastreo` problem is dropped (it speaks of Triple Whale parameters), and the verdict labels are Triple Whale's. The sync bar is `data-poll-job` over the live job ids of `tareas_mr.trabajos_del_panel` (syncs and the evaluation in one read). The only route that calls Meta when opened is `cuentas` (GET, the «Elegir cuentas» selector → `meta_conexion.listar_activos`); `cuentas` (POST) adds only accounts the token SEES (an id typed by hand is ignored), keeps ones already in the project even if the token no longer sees them, and enqueues the first copy of each new one; `cuentas/<act>/pais` changes a country (404 foreign, 400 bad code); `sincronizar` is «Actualizar ahora». Every POST rejects `Sec-Fetch-Site` other than same-origin/none and asks for a verified email (the admin is exempt; the Blueprint copies `dashboard._requiere_correo_verificado` because it cannot import `dashboard`). A POST of `cuentas` without the `pais_<act>` field keeps the saved country; sent empty it clears it.

**NVP in the tab (2026-10-09, asked by the HappyFlops client: «see if it is TOF, MOF or BOF»; spec `2026-10-09-nvp-visitantes-nuevos` §4.2).** Meta has no new visitors: they come from the Triple Whale copy (`tw_anuncio_dia`, channel facebook-ads, same ids as Meta). `panel.con_triple_whale` (one query on `tw_tienda`) decides: without a store no visitor query runs, no column or KPI is painted, and a line links to `#triplewhale` («Conecta Triple Whale para ver el % de visitantes nuevos (NVP).»). With a store, `_nvp_panel` runs ONE `triple_whale.datos.visitantes_por` per level and page over the panel's own `desde..hasta` (accounts —also the KPI, the SUM of the accounts in scope; the account id is asked both as `act_…` and bare—, campaigns, the ad-set page, the ad page; each «Ver más» adds the check and one read of its level): +1 query without Triple Whale, +5 with it, constant with the rows (`tests/test_meta_rend_nvp.py`). Visitors are pasted AFTER `evaluar`, so no verdict changes. The chip is always `cx.nvp(nuevos, visitantes)` (column right after ROAS, KPI tile `.meta-kpi-nvp`); «NVP de las cuentas con Triple Whale: 🇳🇴 Noruega» names the accounts it comes from when only some have visits (today only Norway is connected).

**E2 «Diagnóstico» and «Segmentos» (2026-10-10, spec E2 §6, §9, §10).** `recomendaciones.py` is PURE (no database, Flask, network or Claude): `calcular(entrada)` takes what the panel already read and returns recommendations `{id, nivel alta|media|baja, tipo, cuenta, cuenta_nombre, titulo, que_hacer, por_que, impacto {monto, moneda, texto}|None, objetos [{nivel, id, nombre}] (at most `MAX_OBJETOS` = `administrador.MAX_IDS`), enlace}` sorted by level and then by `impacto` per day (nominal across currencies: PND-266). Nine `TIPOS`: `cuenta_estado`, `cuenta_roas_bajo`, `aprendizaje_limitado`, `perdedores_gastando`, `anuncios_con_problemas`, `escalar`, `fatiga`, `segmento_caro`, `concentracion`; thresholds are the constants at the top of the file (a spec §6 change edits them there). `escalar` treats a CBO campaign as out of limited learning when less than half its 7-day spend is in FAIL ad sets and counts `WITH_ISSUES` ads as active (E2-R3: real HappyFlops data, 70 % of ad sets in FAIL). **`TIPOS_ALTA`** = the types some rule can mark «alta» (`cuenta_estado`, `cuenta_roas_bajo`, `aprendizaje_limitado`, `perdedores_gastando`, `anuncios_con_problemas`): the copy stores only those for Alertas and each has its title in `alertas.TEXTOS_META_RENDIMIENTO`; a test checks that `TIPOS_ALTA`, the types the rules can mark «alta» and those texts agree, so a rule that becomes «alta» must be added to `TIPOS_ALTA` and to the texts (the test only finds literal «alta» levels: PND-267). **Huella = id (E2-R4):** the recommendation `id` is the full sha256 hex that `alertas.HUELLA_VALIDA` accepts (`huella_recomendacion`); the `AGREGADOS` types (everything of an account in one card: the five above) hash tipo + cuenta + nivel, because their object list changes every copy and a dismissed alert must not come back every 3 h (it does come back if the level changes); the others hash tipo + cuenta + the sorted object ids (a segment: `dim:clave`). The rules ALWAYS look at the last 7 and 30 days up to `hoy`, whatever the panel period (the copy computes the same thing for Alertas without a period). `panel.contexto` adds `recomendaciones`, `conteo_recomendaciones`, `segmentos` and `evaluacion`. `_entrada_reglas` builds the rules' input from what the panel already read — the account-day read widened to the last 30 days, the per-ad 7-day read (`gasto_7` and the per-ad-set 7-day sums by `_por_conjunto`), the 30-day ad read when the period is 30, and the single `datos.alcance_varios` read that gives both the period's reach and the 7-day campaign frequency of the fatigue rule — plus at most FOUR queries: `datos.objetos_activos` (ACTIVE campaigns and ad sets), the 30-day ad read for other periods, ONE `datos.desgloses` read for both windows (the rules' 30 and the «Segmentos» window, the nearest of 7/30 to the period; each row says its `ventana`), and `datos.evaluaciones_panel` (one query, below). **Query budget:** `tests/test_meta_rend_panel.py::test_pocas_consultas_con_tres_cuentas` holds ≤ 18 for every period (17 with 7 and 30 days, 18 with 14 and 90), with three accounts in three currencies and ten stored evaluations (a ready one behind nine failures, the worst shape), exactly one `FROM meta_evaluacion` and one `FROM meta_alcance`; nothing grows with accounts, rows or evaluations. Breakdowns older than 48 h (`HORAS_DESGLOSE_VIGENTE`; the copy fetches them every 20 h, so older means a combination keeps failing) feed neither `segmento_caro` nor «Segmentos», which says «Hay desgloses de X con datos de hace N días» instead. «Segmentos» (`panel.segmentos`) sums by key when the accounts share a currency, else one table per account; it flags a row whose `segmento_caro` id (`huella_recomendacion("segmento_caro", act, "media", ["dim:clave"])`) is among the rules' output (the mark comes from the 30-day rule even on the 7-day table: PND-263), shows the 10 with most spend (a ≥ 10 % segment always fits) and names rows with `recomendaciones.nombre_segmento`. Templates: `_meta_diagnostico.html` right after the KPIs (cards by priority, «Ver en el Administrador de anuncios» `target="_blank" rel="noopener noreferrer"`, fatigue cards also link `#meta-evaluacion`, more than 6 inside `<details>`; Meta names only autoescaped) and `_meta_segmentos.html` at the end; CSS `.meta-diag*`/`.meta-seg*` in `pantallas/meta.css`. **Alertas source** (skill `alertas`, fila 13): `panel.recomendaciones_de_cuenta(cliente, act, hoy=None)` is the same computation for ONE account with no Flask or token; at the end of a SUCCESSFUL `meta_rend_sincronizar`, `tareas.meta_rendimiento._guardar_alertas` stores the «alta» ones as `meta_cuenta.extra.alertas = [{tipo, huella}]` (via `cuentas.actualizar_extra`; no title: Alertas builds it in the viewer's language; a failure is logged by type and never fails the copy) and `alertas._fuente_meta_rendimiento` turns them into `atencion` alerts of the «decision» group, key `meta_rendimiento:<tipo>:<act>`, to the Meta tab, with ONE query (`cuentas.listar`) and no rule computed on page load. A copy that keeps failing leaves its stored alerts forever (PND-262).

**E2 «Evaluar con IA» backend (2026-10-10, branch meta-e2, spec E2 §8 and §11; the screen is Task 6, the measured price Task 7).** The one thing in this package that CHARGES. `analisis.py` reuses `triple_whale.analisis` instead of copying it (`muestra`, `copiar_miniaturas(carpeta="meta_rendimiento")` — the folder matters: with TW's, Meta evaluation 3 overwrote TW evaluation 3's thumbnails —, `visuales`, `imagenes_para`, `con_piezas_creatv`, `llamar_con_correccion`, `parsear(origen="meta")`, `texto_error`). `analisis.preparar(cliente, dias, cuenta)` runs in the ROUTE, inside `idiomas.en_idioma(<project language>)` (what is stored and sent to Claude), over the local copy only: the sample (up to 6 winners + 4 losers of `panel._evaluar` for the scope the person is looking at, refs A1…), the first 12 rule recommendations (`recomendaciones.calcular` on the last 7/30 days, each with `ref` R1…), and `extra` = `{dias, cuenta, hoy, meta_roas, meta_roas_proyecto, ventanas {corto: panel.DIAS_SEMANA, largo: panel.DIAS_REGLAS}, resumen: [per account 7 and 30 days vs the previous 7/30, reach and frequency 7/30, active ad sets in FAIL and their share of 7-day spend], segmentos: {act: top 5 30-day segments by spend, a segment with ≥ 99 % of its dimension skipped}}`; `datos.crear_evaluacion(..., extra=)` stores it so the task never depends on the panel. **Disconnecting deletes the copies, the evaluations and their thumbnails (R21, E2-R2).** The privacy policy and `/eliminar-datos` promise it: disconnecting Meta, leaving agency mode, `desasignar` and disconnecting the agency delete the copied metrics of the project and free its accounts, through `dashboard._soltar_cuentas_meta(cliente)`. It does three independent things, in THIS order, each in its own try/except (if one fails the others still run; the disconnection stays done; only the error TYPE is logged and ONE warning flashes): (1) `cuentas.elegir(cliente, [])` (copies and rows of the accounts); (2) `analisis.claves_miniaturas(cliente)` reads the R2 keys of the thumbnails the evaluations copied (`clientes/<c>/meta_rendimiento/eval<id>_<ref>.jpg`: from a `lista` row only the ads whose thumbnail was copied, from one that did not finish every ref, never a Creatv piece's) and `datos.borrar_evaluaciones` deletes the rows, which hold Meta ad names and metrics (the `gasto` rows stay: it was paid); (3) only AFTER the rows, `analisis.borrar_claves` deletes the keys with ONE R2 client (`r2_uploader.delete_files`, never raises, returns (borradas, fallos)) — so a slow or down R2 can never leave Meta names or metrics stored. If the keys cannot be read, or R2 fails, the warning says so; a failed rows delete is retried by the next disconnection (its keys are recomputed from the surviving rows). `meta_agencia.desasignar` and `meta_conexion.borrar` do NOT delete anything by themselves: **any new caller must call `_soltar_cuentas_meta`** (PND-207: move it into the domain layer). The warning text says «métricas copiadas» even when only evaluations or thumbnails failed (PND-267). In agency mode the selector says «Todavía no disponible» (spec §2.10; PND-197).

**Traps.** (1) The token never reaches an error, flash, event, log or template: `graph` summarizes a network error with `type(e).__name__` (the `str` of a `requests` exception carries the URL with `access_token`), Meta's text goes through `cola.sin_token` and the exact token value is struck out; `paging.next` carries the token, so it is never logged or followed. (2) Reach is unique people: it is NOT additive across days or accounts (`totales_por_cuenta` leaves it out on purpose; the period's reach comes from `datos.alcance` at the nearest window, and «Todas» shows the sum of per-account reach, so people on two accounts count twice). Reach of a campaign that stopped delivering stays at its last value (PND-199). (3) Budgets arrive in the currency's minor unit as text (`sync._presupuesto` divides by 100 except `tareas.meta.MONEDAS_SIN_DECIMALES`), and «0» means no budget at that level (budgets are mostly on the ad set), never 0. (4) `estado` has two odd values: `ARCHIVED` and None (Meta no longer lists it); both have labels in `panel.ESTADOS`. An ad paused or archived after the last full listing keeps showing `ACTIVE` for up to ~20 h, because the 3-hourly runs list only the ads that deliver or wait and `datos.activos` counts that stale state. (5) Purchases are the first present type of `graph.TIPOS_COMPRA` (`purchase`, `omni_purchase`, `offsite_conversion.fb_pixel_purchase`), never their sum. (6) Thumbnails are Meta's signed URLs hot-linked with `loading="lazy"`: they expire and the picture breaks until the next refresh (daily for ads with spend in the last 30 days, see «Thumbnails»; PND-194 keeps the copy to R2). (7) The ad set's frequency is not copied, only account and campaign reach (PND-195). (8) «Todas» orders by the nominal amount, so with mixed currencies the order is not by value (PND-196). (9) Every user-visible string of the package goes through the catalog (`PAQUETES` in `catalogo_i18n.py` includes `meta_rendimiento`; the statuses live in `panel.ESTADOS`/`APRENDIZAJE`/`OBJETIVOS` with `N_`). (10) The first real copy of a new account is the only real test of a change to `sync.py`: run it against a copy of the database (the lessons of the Norway and Netherlands runs are the rulings R8–R14). (11) «Evaluar con IA» is PAID and the screen's number must hold: the button sends `n` and `precio_visto` and the route re-computes both (E2-R6); never correct a paid answer for figures (E2-R5); never lower `MAX_TOKENS` below what a whole answer needs (adaptive thinking spends from the same cap: 16 000 failed 3 of 3 on real data); any change to `analisis.py`'s prompt, instructions, validation or `MAX_TOKENS` goes through the `eval-claude` skill with real cases and a re-price of `evaluacion_meta`. (12) Anything that deletes `meta_evaluacion` rows must delete their R2 thumbnails too, AFTER the rows (see «Disconnecting»). (13) Rows of `meta_desglose` older than 48 h are not trusted by any reader: a new reader must apply `HORAS_DESGLOSE_VIGENTE` too.
